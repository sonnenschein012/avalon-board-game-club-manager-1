# 제품 완성 계획

3개월 동안 실제 운영에 사용하는 기능의 UX/UI와 작업 효율을 다듬는다. 기본적인 사용법 인수인계는 완료된 것으로 보고, 후임자는 저장소의 문서·지식 그래프·테스트와 코딩 AI를 이용해 유지보수한다. 데이터 내보내기와 면접 기록의 범위는 [운영 가이드](operations.md)의 기준을 따른다.

## 첫 검토 범위

2026-09-13에 Scenario Lab의 회원 기본 화면, 조 편성 혼잡 화면, 면접 대용량 화면을 확인했다. PC 1440px와 모바일 390px에서 화면을 보고, 실제 앱이 사용하는 컴포넌트와 호출 위치를 대조했다. Scenario Lab의 상단 메뉴·fixture 데이터·일부 동작은 실제 앱과 다르므로 이 결과는 세 화면의 표시와 조작에 관한 개선 제안이다. 앱 전체 기능, 운영 데이터와 배포 상태를 검증한 결과는 아니다.

## 우선 개선 후보

아래 항목은 구현 전 제안이다. 실제 사용 기기의 비중에 따라 모바일 작업의 순서를 조정한다.

| 순서 | 관찰한 내용 | 제안 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 면접 시간표 앞에 확정 안내된 지원자 버튼을 모두 나열한다. 대용량 fixture에서는 PC에서도 여러 줄을 차지해 시간표가 아래로 밀린다. | 확정 명단을 인원 요약과 펼치기로 제공하고, 시간표를 바로 볼 수 있게 배치한다. 기존 개별 변경 동작은 펼친 목록에서 유지한다. | 기본 화면의 확정 명단은 접혀 있고, 시간표에 바로 접근한다. 펼치면 전체 대상과 기존 변경 확인 절차를 사용할 수 있다. |
| 2 | 조 편성의 모드 진입, 실제 편성 실행, 모임 시작 버튼이 두 영역에 나뉜다. 모바일에서는 미배정 명단 다음에 조가 나와 두 영역 사이 이동이 길다. | 명단 준비·편성 설정·편성 실행·모임 시작의 버튼 이름과 위치를 정리한다. 모바일을 실제로 사용한다면 미배정 명단과 조 사이를 바로 이동하는 조작을 추가한다. | 각 버튼의 결과가 이름으로 구분되고 현재 배정·미배정 인원과 다음 행동을 쉽게 확인한다. 모바일 개선 시 기존 드래그·스크롤·초안 유지 동작을 보존한다. |
| 3 | 회원 수정·삭제 아이콘에 접근성 이름과 툴팁이 없고, 필터의 키보드 포커스 표시가 없다. 같은 조작이 여러 곳에서 반복된다. | 회원 화면에서 버튼 이름, 클릭 영역, 검색 입력의 이름과 포커스 표시를 먼저 정리하고 공통 기준으로 삼는다. | 수정·삭제의 대상과 동작이 식별된다. 키보드로 검색·필터·편집에 접근할 때 현재 위치가 보이고, 선택·저장 동작을 유지한다. |

### 코드 근거

- `src/components/InterviewSchedulePanel.tsx:307` — 확정 안내된 지원자 전체를 시간표 앞에서 버튼으로 렌더링한다.
- `src/components/InterviewSchedulePanel.tsx:374` — 모바일 시간표 설명에 내부 용어 `revision`을 표시한다. 업무 용어로 바꿀 후보다.
- `src/components/AttendancePage.tsx:84`, `src/components/GroupsCanvas.tsx:83` — 자동 편성 모드 진입과 편성 실행이 다른 영역에 있다.
- `src/components/AttendancePage.tsx:114`, `src/components/UnassignedPool.tsx:26` — 모바일에서 미배정 명단이 조 영역 앞에 놓인다.
- `src/components/MemberList.tsx:181`, `src/components/MemberList.tsx:241` — PC·모바일 수정·삭제 아이콘의 이름이 없다.
- `src/components/MemberFilters.tsx:60` — 검색 입력에 label 또는 aria-label이 없다.
- `src/components/MemberFilters.tsx:74` — 필터가 outline을 제거하고 대체 포커스 표시를 제공하지 않는다. 다른 두 필터도 같다.

버튼 이름과 포커스 검토 기준: [Web Interface Guidelines](https://raw.githubusercontent.com/vercel-labs/web-interface-guidelines/main/command.md).

## 진행 순서

1. 첫 작업으로 면접 시간표의 확정 명단 요약을 구현하고, 변경 전후 화면을 비교한다. 면접 상태나 배정 정책은 이 작업에 포함하지 않는다.
2. 첫 2주 안에 위 후보 중 실제 사용에 효과가 있는 항목을 끝내고, 버튼·검색·필터의 공통 표시 기준을 정한다.
3. 다음 6~8주는 한 번에 한 업무 화면을 개선한다. 각 작업에 실제 불편과 완료 기준을 먼저 적고, 기능이 충분한 화면은 유지한다. 남은 시간을 채우기 위해 기능을 추가하지 않는다.
4. 마지막 2~3주는 발견된 오류, 기능 간 일관성과 릴리스 검증을 마무리한다. 배포는 운영 가이드의 별도 절차를 따른다.

첫 면접 변경은 Scenario Lab에서 기본·대용량·변경 요청 상태의 표시와 펼치기를 확인한다. 표시만 바꿀 때는 배정 알고리즘과 Firestore 계약을 바꾸지 않는다. 실제 저장 동작을 변경하면 Emulator Design Lab의 해당 시나리오까지 검증한다. 회원과 조 편성은 변경한 조작에 맞는 기존 테스트를 사용한다.

작업 완료는 화면 변경, 관련 검증, 완료 기준 충족으로 판정한다. 아직 확인하지 않은 전체 앱의 사용성 문제나 가상의 데이터 손실을 이 목록의 확정 결함으로 추가하지 않는다.
