# 조 인원 구성 모델

2026-10-08 기준. 운영자와 합의한 선호를 `src/domain/matching/groupSizing.mjs`에 구현하고 앱의 자동 편성에 연결했다. `scripts/group-sizing-prototype.mjs`도 같은 구현을 호출한다. 저장 형식과 Firestore 규칙은 유지했다. 수동 배치 하한을 포함한 독립 완전 열거 검증과 다양한 규모의 모의 편성을 수행했으며 배포 상태는 [운영 이력](operations.md)에 기록한다.

## 목적과 확정된 경계

- 운영자가 조 개수를 정한다. 자동으로 조를 추가하거나 삭제하지 않는다.
- 조별 인원은 전부/일부/전혀 지정하지 않을 수 있다.
- 인원 구성을 먼저 하나로 확정하고, 이후 그 인원을 조건으로 개인 효용·비용에 따라 사람을 배치한다. 개인 효용을 인원 구성의 동점 처리에 사용하지 않는다.
- 우선순위는 실행 가능성 → 운영자 설정 → 인원 구성 기준이다.
- 실행 가능한 범위는 조당 4~10명이다. 참석자 수가 `4 × 조 개수` 미만 또는 `10 × 조 개수` 초과이면 조 개수 조정을 안내한다. 범위 밖 크기를 만들어 실행하지 않는다.
- 운영자 지정 인원을 그대로 지킬 수 없다면 지정한 조들의 `|결과 인원 - 지정 인원|` 합을 최소화한다. 미지정 조에는 이 비용을 부과하지 않는다.
- 5개를 초과한 조 수만큼 4명 조를 우선 확보한다. 고정 설정 보존 뒤의 기준이며, 불가능하면 가능한 만큼만 확보한다. 특정 번호의 조를 추가 조로 지정하지 않는다.
- 추가 조 몫으로 확보한 4명 조는 기본 조의 반복/4명 비선호 평가에서 제외한다. 그 외 4명 조는 일반 평가에 포함한다.

## 현재 계산 절차

`src/domain/matching/groupSizing.mjs`는 가능한 4~10명 인원 조합을 중복 없이 열거한다. 각 조합의 인원을 실제 조 ID에 연결하면서 운영자 지정 인원의 총편차를 최소화한다. 조 ID가 달라도 지정 인원은 해당 조에 귀속된다.

후보의 다음 값을 **위에서부터 사전식으로 최소화**한다. 앞 항목이 다르면 뒤 항목의 개선으로 역전하지 않는다.

1. 운영자 지정 인원의 총편차
2. 추가 조 몫에서 확보하지 못한 4명 조 수
3. 8명 이상 조 수가 하나를 초과하는 정도
4. 7명 이상 조 수가 두 개를 초과하는 정도
5. 7~10명 각각에서 동일 인원의 중복 수: `Σ max(0, 해당 인원 조 수 - 1)`
6. 9명 또는 10명 조의 수 — 두 크기에 동일한 값 적용
7. 아래의 일반 선호 점수

이 순서는 기존 비교 사례를 재현하는 현재 모델이다. 특히 4번과 5번의 독립적인 충돌 순서는 별도 사용자 판단으로 확정된 사실이 아니라 모델의 가정이다. 일반적인 5개 조 구성에서는 이 둘이 함께 위반되는 경우가 많다.

5·6명 조를 중심으로 구성하되, 5개 이상을 운영할 때는 큰 조 하나를 선호한다. 2~4개 조에서는 큰 조가 없다는 불이익을 제거한다. 1개 조도 같은 방식으로 계산하며 가능한 인원 구성은 총인원 하나뿐이다.

### 일반 선호 관계식

추가 조 몫의 4명 조를 제외한 뒤, 각 인원 `s`의 조 수를 `c_s`, 7명 이상 조 수를 `L`이라 한다.

`P = Σ max(0, c_s - 2)² + 1.5 × c_4 + 0.75 × I(전체 조 수 ≥ 5이고 L = 0) + 0.25 × max(0, L - 1)`

낮을수록 선호한다. 같은 인원이 두 조 이하면 반복 비용은 0이고, 세/네/다섯 조면 1/4/9다. 5·6명은 별도 크기 비용이 없고, 다른 크기는 상위 제한 또는 4명 비용으로 구분한다. 5명과 6명 사이의 고유 우열은 추가하지 않았다.

계수 **1.5, 0.75, 0.25 및 제곱 형태는 검증용 잠정값**이다. 선택 사례를 설명할 수 있다는 의미이지, 이론적으로 유일하게 도출됐거나 실제 만족도로 추정된 값이 아니다. 코드에서는 4배 정수 점수로 비교해 소수점 오차를 피한다.

### 최종 동점 처리 — 잠정 기본값

정책 점수가 전부 같으면 인원을 내림차순으로 정렬한 벡터를 작은 순서로 비교한다. 최대 인원이 작은 후보, 같으면 다음으로 큰 인원이 작은 후보를 고른다. 예: 18명·3개 조의 `7·6·5`와 `8·5·5` 중 전자.

이는 효용 차이를 새로 가정하는 것이 아니라 단일 결과를 만들기 위한 절차다. 9명과 10명의 정책 점수는 같지만, 최종 동점 처리에서 숫자로 구분될 수 있다. 결과에 `policyTieCount`를 남겨 이 구분을 확인할 수 있다.

조 ID별 배분까지 동점이면 문자열 ID의 고정 순서를 사용한다. 고정 목표를 숫자와 ID 순으로 정렬한 뒤 최소편차 배분을 구하고, 남는 인원은 ID 순의 미지정 조에 큰 값부터 부여한다. 입력 배열의 순서를 바꾸어도 조 ID별 결과는 같다. 이 배분 절차는 개인 효용을 평가하지 않는다.

## 입력·출력과 재현

```js
solveGroupSizes({
  total: 30,
  groups: [
    { id: 'a', targetSize: 7 },
    { id: 'b' }, { id: 'c' }, { id: 'd' }, { id: 'e' },
  ],
});
```

`targetSize`의 `null`, `undefined`, `0`은 미지정이다. 0은 기존 화면의 빈 값 표현이다. 양의 정수 지정은 4~10 밖이어도 선호로 받아 범위 안으로 최소 조정한다. 음수·소수·중복 ID·잘못된 총인원은 입력 오류로 거부한다.

성공 결과에는 인원 벡터, ID별 배분, 자동 조정 내역, 운영자 설정 편차, 규칙별 위반량, 일반 선호 점수의 내역, 후보 수, 정책 동점 수가 있다. 총인원이 범위 밖이면 부분 배정 없이 `infeasible / change-group-count`를 반환한다. 파일·서비스를 쓰지 않는 순수 계산이다.

```powershell
node scripts/group-sizing-prototype.mjs
node --test scripts/group-sizing-prototype.test.mjs
```

추가 확인 결과:

- 30명·5개 조에서 한 조를 7명 지정: `7·6·6·6·5`. 지정한 조 ID에 7명을 유지한다.
- 34명·6개 조: `8·6·6·5·5·4`. 추가 조의 4명에는 일반 선호 불이익을 주지 않는다.
- 33명·6개 조에서 `5·5·5·6·6`을 지정: 미지정 조는 6명. 지정 인원을 변경해 억지로 4명 조를 만들지 않는다.
- 42명·7개 조에서 `5·5·6·7`을 지정: 나머지는 `9·6·4`. 추가 조 몫 둘 중 하나만 4명으로 확보하며 8명 이상 조는 하나를 유지한다.

24개 테스트가 합의 사례, 부분/전체 지정, 부족/초과, 추가 조 예외, 입력 오류, 동점과 ID 안정성을 확인한다. 별도의 조 ID별 완전탐색과 최소편차를 대조했다. 1~10개 조의 모든 가능한 총인원 **340개 경우**에서 인원 보존·4~10 범위·반복 실행 일치를 확인했다. 사례 통과는 전체 선호가 확정됐다는 의미가 아니다.

## 앱 연결 경계

인원 모델은 조 ID, 지정 인원, 수동 배치 인원수에 따른 하한만 받는다. 사람의 성별·학번·요청·운영진 역할은 받지 않는다. 수동 인원이 4명을 초과하면 정원별 남은 개수를 상태로 하는 동적 계획법으로 조 ID에 연결하며, 하한 미만 정원은 후보에서 제외한다. 하한과 4~10명 범위를 동시에 지킬 수 없으면 실행하지 않고 조 수나 수동 배치 조정을 안내한다. 저장 컬렉션이나 보안 규칙에 영향이 없다. 기존 지식 그래프는 일반 미커밋 작업 동안 stale 상태를 유지한다.

2026-10-01 후속 합의: 동반 요청을 모두 담을 수 있는 인원 구성만 남긴다는 이전 제안은 철회했다. 요청 집합이 사용자 지정 정원이나 최대 10명을 초과하는 경우를 같은 문제로 취급한다. 요청 때문에 인원 구성을 다시 결정하지 않으며, 확정된 인원 안에서 요청을 최대한 충족하고 미충족을 안내한다. 요청의 연결 집합을 분리할 수 없는 실행 제약으로 취급하지 않는다.

운영자가 요청 상대들을 서로 다른 조에 수동 배치했다면 수동 배치를 유지하고 해당 동반 요청의 미충족을 안내한다. 요청을 위해 자동으로 수동 배치를 옮기지 않는다. 직접 충돌하지 않는 요청까지 일괄 무시하지 않는다. A와 C를 서로 다른 조에 수동 배치했고 B가 양쪽에 요청으로 연결된 경우에도, A와 C를 유지한 채 다음 순서로 B의 배치를 비교한다.

1. 명시적인 동반 요청의 충족 평가
2. 운영진 배치: 운영진 없는 조를 줄이고, 불가피하면 4명 조부터 예외 허용
3. 성별·학번·재회 등 추론적인 개인 효용·비용 평가

명시적 선호는 추론적 선호보다 우선한다. 동반 요청 평가는 단순한 충족 쌍 수에서 개인별 충족 정도의 한계 효용 체감을 반영하는 방향으로 변경했다. 이미 동반 상대가 있는 사람의 추가 요청보다, 아직 아무도 없는 사람의 첫 요청 충족에 더 큰 가치를 둔다. 체감하더라도 하위의 추론적 개선이 상위의 명시적 선호를 역전해서는 안 된다. 개인별 요청 상대 수를 `n_i`라 할 때 점수는 `Σ ln(1+n_i)`로 확정했다. 이후 합의한 관계식과 검증 결과는 [개인 효용 모델](group-utility-model.md)에 정리했다.

한쪽 이상이 요청한 두 사람은 하나의 요청 관계로 취급하고, 양쪽이 적어도 중복 가산하지 않는다. 관계 충족 효과는 두 사람에게 적용한다. 함께 배치된 요청 상대 수가 늘면 성별·학번 구성의 영향을 줄이는 효과도 커지되, 추가 상대의 완화 효과는 체감한다. 재회 비용에는 이 완화를 적용하지 않으며 직접 요청 상대와의 재회 비용은 제외한다. 요청했지만 함께 배치되지 않은 상대는 완화 효과에 포함하지 않는다. 이 관계식은 앱의 개인 효용 평가기와 독립 합성 검토 평가기에 구현했다.

미충족 안내는 기존 `GroupsCanvas`의 조원 목록 아래 재회 경고와 같은 주황색 배경·테두리·경고 아이콘을 사용한다. 일회성 toast나 실행을 막는 모달이 아니라 해당 조에서 계속 확인할 수 있는 안내다. 문구 예: `동반 요청 미충족: A님과 B님은 수동 배치를 유지하여 서로 다른 조에 배치되었습니다.` 관련 두 조에 표시하고, 수동 조정으로 요청이 충족되면 제거하는 방식을 기본안으로 둔다. 표시 코드는 앱에 연결했으며, 이 문구는 두 당사자가 서로 다른 조에 수동 고정된 것이 확인될 때만 사용한다. 그 외에는 원인을 단정하지 않는다. 조 인원 조정과 규칙 완화 안내는 화면 상단에 표시하며 마지막 실행의 입력·결과가 변경되면 제거한다.

기존 재회 경고는 `attendanceHelpers.getReunionWarnings` → `useAttendanceLogic` → `AttendancePage` → `GroupsCanvas` 경로로 전달된다. 기존 경고의 최신 전체 세션 기준과 새 개인별 재회 평가를 혼동하지 않는다. 새 작업은 표시 형식을 재사용하는 것이며 기존 재회 판단 로직을 그대로 동반 요청에 적용하지 않는다. 기존 attendee/member ID 변환과 계획/확정 세션 구분도 유지해야 한다.

운영진은 조마다 최소 한 명을 목표로 하며 부족하면 4명 조부터 예외로 둔다. 조원에 따른 세부 예외는 운영자가 결과를 조정한다. 개인 효용·비용의 관계식과 탐색 알고리즘은 이 인원 모델의 구현 범위가 아니다.
