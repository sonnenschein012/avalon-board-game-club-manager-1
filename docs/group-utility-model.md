# 개인 효용 모델

2026-10-08 기준. `src/domain/matching/personalUtility.ts`와 `autoAssignAlgorithm.ts`를 실제 앱의 편성·개인 점수 창·시뮬레이션 내보내기에 연결했다. `scripts/group-utility-prototype.mjs`는 독립적인 검토 평가기로 남긴다. 요청 완화·재회 감쇠·환산 보호 조정과 모의 검증을 수행했다. 통계 수식·저장 문서·운영 데이터는 변경하지 않았다. 조 인원 결정은 [조 인원 구성 모델](group-sizing-model.md)을 먼저 적용하며 배포 상태는 [운영 이력](operations.md)에 기록한다.

## 평가 순서

확정된 조 인원을 채우고, 수동 배치한 사람을 유지하며, 모든 참석자를 정확히 한 번 배치한 후보만 평가한다. 현재 검증용 코드는 잘못된 후보를 입력 오류로 거부한다.

1. 명시적인 동반 요청 점수 `R` 최대화
2. 운영진 없는 조 수 최소화. 같은 수라면 4명 아닌 조의 운영진 공백을 최소화
3. 개인 순효용에 최대 2배 보호를 적용한 전체 점수 `W` 최대화

동반 요청이 정원을 넘거나 수동 배치와 충돌해도 조 인원을 다시 정하지 않는다. 요청을 덜 충족한 배치는 운영진 분산이나 추론적 점수가 좋아져도 앞설 수 없다. 상위 기준이 같은 경우에만 다음 기준을 비교한다. 모든 점수가 같으면 재현 가능한 탐색 순서에서 먼저 선택된 배치를 유지한다. 독립 검토 평가기의 완전 열거에서는 ID 순서로 동점을 처리한다.

## 요청사항 인식 정책 (2026-10-08 합의)

- 자유서술에서 동반 상대를 찾는 방식은 현행 `groupCostContext.ts`의 이름 포함 검사(`attendee.request.includes(requestedMember.name)`)를 유지한다. 요청자를 회원과 연결한 뒤 전체 회원 중 본인을 제외하고 검사한다.
- 문장 의미·부정 표현의 자동 판별, AI 해석, 별도의 후보 확인 UI는 추가하지 않는다. 운영진은 기존 요청사항 확인과 수동 배치를 활용한다. 동명이인·부분 문자열·부정 표현을 구분하지 못하는 현행 한계도 이번에는 변경하지 않는다.
- 이름이 매칭되지 않은 원문을 동반 요청이라고 단정하거나 동반 요청 미충족으로 경고하지 않는다.
- 상대가 이름으로 확인됐지만 해당 모임에 불참한 경우에는 요청 평가에서 제외하고, 불참으로 반영하지 못했다는 안내를 표시한다. 이 안내는 요청자가 속한 조에 표시한다. 아직 미배정된 요청자의 불참 상대 안내는 화면 상단에 표시한다.

## 확정한 함수 형태

### 동반 요청

`n_i`는 개인 i와 실제로 같은 조에 있는 **직접 요청 관계의 상대 수**다. 한쪽만 요청해도 양쪽에게 적용하고, 양방향/반복 요청은 같은 쌍으로 한 번만 센다. A–B–C 요청에서 A–C를 자동으로 새 요청 관계로 만들지 않는다.

`R = Σ_i ln(1 + n_i)`

처음 상대가 생기는 효과가 가장 크고, 추가 효과는 양수이면서 체감한다. A에게 네 사람이 요청하고 모두 함께 있으면 `ln(5) + 4 ln(2)`다. 요청 상대가 나뉘어 있으면 그 쌍은 충족 수나 완화 효과에 포함하지 않는다.

구현은 `P = ∏_i(1+n_i)`를 BigInt로 비교한다. `R = ln(P)`이므로 선호 순서는 같지만 소수점 합산 오차 때문에 동률을 잘못 판단하지 않는다. 화면 검토용으로 로그 점수도 함께 반환한다.

### 성별과 학번

동성 수 `s_i`, 이성 수 `o_i`는 본인을 제외한다.

- 동성 효용: `U_s = A_s(1 - exp(-k_s s_i))`
- 이성 효용: `U_o = A_o(1 - exp(-k_o o_i))`
- 조건: `k_s > k_o > 0`, `A_s(1-exp(-k_s)) > A_o(1-exp(-k_o))`

두 효용을 더한다. 동성 쪽이 더 빨리 포화되고 첫 동성 한 명의 효용이 더 크지만, 효용 상한의 대소는 별도로 결정한다.

상대 j와의 학번 차이는 선후배 방향을 구분하지 않는 절댓값 `d_ij`다.

- 상대별 비용: `c_ij = B(1 - exp(-h d_ij))`
- 조 전체의 개인 학번 비용: `C_year,i = -t ln[(1/m) Σ_j exp(-c_ij/t)]`

`m`은 본인 외 조원 수다. 가까운 사람이 있으면 부담이 줄고, 가까운 사람이 추가될 때의 완화는 체감한다. 먼 사람도 계속 평가에 포함된다. 전원이 같은 차이면 그 상대별 비용과 같아진다. 구현은 최소 비용을 빼고 지수를 계산하는 동치식으로 수치 안정성을 확보한다.

### 동반 상대의 완화와 재회

`w_i = exp(-k_request n_i)`

동반 상대가 많으면 성별·학번 구성의 영향이 줄어든다. 추가 상대의 완화 효과는 체감한다. 이 계수는 명시적 요청 점수나 재회 비용에 적용하지 않는다.

각자의 실제 참여 기록을 최근부터 `r=0,1,...`로 센다. 결석한 모임은 이 순서에 들어가지 않는다. 해당 회차에서 j와 같은 조였으면 `I_ij,r=1`, 아니면 0이다.

- 최근 반복량: `H_ij = Σ_r rho^r I_ij,r`, `0 < rho < 1`
- 상대별 재회 비용: `a H_ij^p`, `a > 0`, `p > 1`
- 개인 재회 비용: 직접 요청 상대를 제외한 현재 조원들의 상대별 비용 합

오래된 만남의 영향은 지수적으로 사라지고 반복량이 커질수록 비용은 가파르게 증가한다. A와 B의 실제 참여 이력이 다르면 서로의 재회 비용도 다를 수 있다. 기록은 편성 전에 발생한 과거 모임만 사용해야 하며, 프로토타입 입력은 이미 과거·최신순으로 준비됐다고 전제한다.

### 개인 순효용과 환산 보호 (2026-10-08 변경)

`u_i = w_i (U_s + U_o - C_year,i) - C_reunion,i`

전체 편성에서 평가하는 N명의 평균을 `mu = (sum u_i)/N`이라 하고, 고정 척도 `s > 0`로 환산한다.

`z_i = (u_i - mu) / s`

평균보다 불리한 사람의 개선을 더 중요하게 보되, 모두의 순효용이 같은 양만큼 이동하면 중요도는 그대로다. 표준편차·최솟값·최댓값·순위로 정규화하지 않으며, 분포를 정규분포로 변환하는 기능도 아니다. 척도 s는 모임마다 다시 추정하지 않는다.

실제 비교 점수는 다음과 같다.

`W = 1.5 sum(u_i) - 0.5 s sum(log(cosh(z_i / 2)))`

`a_i = tanh(z_i/2)`와 전체 평균 `a_bar`를 이용하면 개인 효용의 작은 개선에 대한 중요도는 실제 도함수다.

`dW/du_i = 1.5 - 0.25 (a_i - a_bar)`

- a는 -1~1 범위이므로 중요도는 1~2 범위다. 따라서 모든 개인의 효용 개선은 전체 평가를 개선하고, 가장 큰 중요도도 가장 작은 중요도의 2배를 넘지 않는다.
- 중요도의 전체 평균은 1.5다. 순효용이 같은 사람은 중요도도 같고, 전원의 순효용이 같으면 모두 1.5다. 낮은 순효용일수록 더 큰 중요도를 받는다.
- 전원의 효용을 c만큼 올리면 W는 `1.5 N c`만큼 증가한다. 중요도가 공통 수준에 왜곡되지 않으면서 전체적인 개선은 평가에 반영된다.
- 총효용이 같을 때는 편차가 작은 분포를 선호한다. 평균과 척도의 모든 영향까지 미분한 중요도이므로, 환산값으로 계산한 임의의 가중치를 효용에 단순 곱하지 않는다.
- `protectedUtility`는 각 개인의 `1.5 u_i - 0.5 s log(cosh(z_i/2))` 평가 기여분이다. 중요도와 순효용의 곱이 아니며 합산하면 W가 된다. 화면은 원래 순효용, 환산 순효용, 실제 개선 중요도, 평가 기여분을 각각 표시한다.

이전에 사용한 절대 기준점 b의 softplus 보호는 이번 합의로 대체했다. 파라미터 `protectionB`를 제거했으며 고정 척도 `protectionS`만 남긴다. 계수 1.5/0.5는 중요도를 1~2 범위로 유지하기 위한 고정 구성이다. 독립 검토 평가기는 평균 중심 softplus의 동치식으로 계산하여 앱의 log-cosh 구현과 대조한다.

보호는 전체 편성에 의존한다. 교환 후보를 평가할 때 교환되는 두 조의 개인 효용만 다시 계산할 수는 있지만, 보호 평균과 점수는 그대로인 다른 조의 사람까지 포함해 다시 계산한다. 조별로 보호한 점수를 단순 합산하지 않는다.

요청이 성별·학번 영향을 완화하면서 양수 순효용을 낮출 수 있는 특성은 유지한다. 명시적인 요청 점수는 여전히 별도 상위 평가다. 이 단계의 점수는 실제 만족도를 측정한 통계가 아니다.

추가로 한 합성 사례에서 기본값, 재회 강화, 요청 완화 강화, 보호 전환 완만화의 네 설정을 비교했다. 요청 비교용 곱은 모두 48, 운영진 없는 조는 하나였으며 같은 배치를 선택했다. 이는 해당 사례의 결과일 뿐, 모든 모임에서 수치에 둔감하다는 근거는 아니다.

## 앱 연결 범위와 다음 단계

- `buildUtilityContext`는 출석 ID와 회원 ID를 구분하고 명부 중복을 검사한다. 현행 이름 매칭을 유지하며 기타/미상 성별과 누락 학번은 양쪽 계산에서 제외한다. 결석 상태와 미등록 출석자는 자동 대상에 포함하지 않는다. 수동 조 안의 미등록·결석 인원은 자동으로 제거하지 않고 오류로 안내한다.
- 재회 이력은 편성일 이전의 확정 세션을 날짜순으로 정렬한 뒤 개인별 참석 순서로 감쇠한다. 당일/미래 기록을 제외한다. 직접 요청 상대의 재회 비용을 면제한다.
- 정원을 하나로 결정한 뒤 8개 시작 배치, 시작당 최대 2,000회 교환 시도와 최대 3회 전체 쌍 교환 점검을 수행한다. 기존 조원은 수동 고정으로 유지한다. 후보 비교 순서는 엄격하지만 탐색은 근사이며 요청 최대 충족이나 전역 최적해를 증명하지 않는다. 동일 입력은 재현 가능한 시드로 탐색한다.
- Worker에서 탐색해 화면을 막지 않는다. 입력 변경/화면 종료 시 Worker를 종료하고 오래된 결과를 버린다. 결과 적용 시 정원과 조원만 바꾸고 조 ID·이름·게임·메모는 유지한다.
- 미충족 요청은 관련 두 조에서 현재 배치를 기준으로 표시한다. 두 당사자가 서로 다른 조에 수동 고정된 것이 확인된 경우에만 그 이유를 안내한다. 그 외에는 같은 조가 아니라는 사실만 알리며 정원 때문에 불가능하다고 추정하지 않는다. 과거 자동 실행의 수동 배치 설명은 입력·결과가 변경되면 사용하지 않는다.
- 점수 창은 개인별 동성/이성 효용·학번 비용·완화·재회 비용·순효용·환산 순효용·개선 중요도·평가 기여분을 보여준다. 요청/운영진/개인 효용을 단일 비용으로 합산하지 않는다. 미완성 배치는 현재 배치된 등록 참석자만 표시한다.
- 시뮬레이션 내보내기는 사용 파라미터, 결정된 정원, 최종 우선순위 지표, 탐색 중 채택 배치의 점수를 제공한다. 개인 이름/요청 원문은 포함하지 않으며 전체 배치의 무작위 분포를 의미하지 않는다.

`REVIEW_PARAMETERS`는 위 초기 운영값을 담는 상수다. 기본 구현 검증은 합성 데이터로 수행하며, 사용자가 제공한 CSV의 오프라인 모의 비교는 별도 비공개 작업 디렉터리에서 실행한다. 회원 이름·원본 CSV·개인별 모의 결과는 저장소에 포함하지 않는다.

### 이번 앱 연결의 기본 확인

- 앱 연결·누락 정보·이력·우선순위·Worker 취소/오류 테스트 13개 통과. 그중 수식 대조는 8명·2개 조의 35개 분할을 독립 검토 평가기와 비교했다.
- 기존 관계식/인원 구성 검토 테스트 46개 통과. 인원 검토 스크립트는 앱과 같은 정원 계산 코드를 사용한다.
- TypeScript, ESLint, 앱 빌드와 운영 번들 분리 검사 통과.
- 로컬 Emulator 합성 데이터에서 실제 편성 Worker 실행, 수동 고정 유지, 4/5명 정원 조정, 요청/불참 안내, 개인 점수 창의 데스크톱·390px 화면 확인을 통과했다.

이는 당시 구현 연결의 기본 확인이다. 이후 조정·모의 비교와 회귀 검증은 아래에 기록한다. 실제 만족도에 따른 파라미터 추정은 별도 운영 관측이 필요하다.


### 환산 보호 변경의 확인

전체 수준 이동에 대한 중요도 불변성, 고정 척도의 유지, 중요도와 실제 수치 미분의 일치, 모든 개인의 단독 개선, 동일 총효용의 균형 선호, 빈 입력/균일 분포/큰 값의 안정성, 그대로인 조를 포함해야 비교가 역전되지 않는 사례를 확인한다. 전체 편성 점수와 화면의 중요도도 같은 평가기로 계산한다. 실제 조 편성의 품질과 환산 척도 2의 적절성은 후속 모의 비교에서 확인한다.

변경 후 합성 앱 테스트 16개와 검토 테스트 46개, 타입 검사·린트·빌드를 통과했다. 로컬 Emulator 화면에서 환산 순효용/개선 중요도 열과 실제 Worker 편성을 확인했다. 초기 명단·명부·이력 조회가 완료되기 전에 편성을 실행하면 새 입력 때문에 취소될 수 있는 문제를 확인해, 세 조회가 모두 성공한 뒤 편성/내보내기 버튼을 활성화하도록 보완했다.

### 배포 전 모의 비교와 한계 (2026-10-08)

사용자가 제공한 세션/회원 CSV를 오프라인에서 다시 편성했다. 각 모임 당시의 참석자·운영진과 해당 날짜 이전의 확정 이력만 사용했다. 원본 요청사항과 수동 고정 정보가 없으므로 모두 요청 없이 재편성했다. 다음 W 값은 이번 수식의 점수이며 실제 만족도 측정값이나 과거 운영 판단에 대한 우열 판정이 아니다.

- 기존/재편성의 개인 순효용·재회 비용·환산값·중요도·전체 점수를 독립 평가기와 대조하여 오차 1e-9 이내로 일치했다. 모든 인원을 중복 없이 정원대로 배치했다.
- 45명 사례는 운영진 7명으로 8개 조를 채워야 한다. 기존 운영진 공백 2개를 4명 조 하나의 공백으로 줄였다. 26명 사례는 공백 1개를 0개로 줄였다.

- 같은 인원 구성이어도 조 ID에 붙은 정원과 탐색 시드가 달라지면 다른 국소해를 찾을 수 있다. 미지정 편성의 W가 기존 정원 재편성보다 항상 높다는 보장은 없다.
- 요청 집중·순환 연쇄·다중 연결·수동 고정 충돌의 8명/2개 조 사례에서 가능한 35개 분할(고정 충돌은 허용 분할만)을 완전 비교했다. 앱 탐색이 요청·운영진·개인 평가 모두 최선인 결과와 일치했다. 이 네 사례를 앱 회귀 테스트에 포함했다. 큰 모임에 대한 최적성 보장은 아니다.
- 수동 배치 하한과 운영자 인원 선호가 엇갈리는 세 조건을 가능한 모든 정원 배정과 대조했다. 최소 인원과 운영자 편차의 우선순위·입력 순서 독립성을 확인했다.
- Node 22.23.2의 단일 실행 측정에서 합성 26/45/60/80명 편성은 각각 약 0.35/1.29/3.53/7.23초였다. 과거 자료 재편성은 약 0.38~1.68초였다. 모바일 Worker의 응답 시간 보장은 아니며 화면은 Worker 실행 중에도 조작 가능하다.
- 로컬 Emulator의 전체 화면 회귀 시나리오 7개를 통과했다. 실제 운영 데이터에 테스트용 편성이나 쓰기를 수행하지 않았다.

최종 검증은 앱 단위 테스트 301개, 환경·정원·독립 효용 검토 테스트 50개, 로컬 화면 회귀 7개를 통과했다. ESLint·TypeScript·Node 22 운영 빌드와 운영 번들 분리 검사도 통과했다. 정원과 독립 효용 검토 테스트는 `npm run test:unit`에 포함해 CI에서도 실행한다.

초기 운영값의 코드 검증과 모의 점검은 완료했다. 운영 만족도를 관측한 통계적 보정은 이번 배포의 완료 조건으로 삼지 않으며, 후속 운영 사례에서 별도로 판단한다.
